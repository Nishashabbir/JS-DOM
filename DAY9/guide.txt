


The connection is not because setTimeout knows about getData(). It doesn't.

The connection is because both getData() and setTimeout() are using the same controller object.

Let's visualize it.

const controller = new AbortController();

This creates one object in memory.

controller
   |
   +--> signal

Now inside getData():

fetch(url, {
    signal: controller.signal
});

Here you're telling fetch:

"Hey fetch, if this particular signal is ever aborted, stop the request."

So internally, fetch keeps a reference to that signal.

fetch
   |
   +-------> controller.signal

Then later:

setTimeout(() => {
    controller.abort();
}, 100);

This doesn't search for a fetch or anything.

It simply says:

"Change the state of THIS controller."

Internally it becomes something like:

controller
    aborted = true

When abort() is called:

controller.signal.aborted becomes true.
The signal fires an "abort" event.
Every fetch that is listening to that signal gets notified.
Those fetches immediately reject with an AbortError.

Think of it like this:

Controller
     │
     ▼
Signal
   │
   ├──── Fetch #1
   ├──── Fetch #2
   └──── Fetch #3

When you do

controller.abort();

it's like pressing one emergency stop button.

Controller
     │
     ▼
Signal  ---> "STOP!"
   │
   ├──── Fetch #1 stops
   ├──── Fetch #2 stops
   └──── Fetch #3 stops

Before starting a new request...

Kill the previous one.

Old Request

↓

ABORT

↓

New Request

First Attempt

You might think:

const controller = new AbortController();

outside the event listener.

Then:

fetch(url,{
    signal: controller.signal
});

and later

controller.abort();

Let's think carefully.

First search
controller

↓

Request 1

Works.

Then:

controller.abort();

Request dies.

Good.

Now user searches again.

Same controller.

controller

↓

Request 2

Will this work?

No.

Here's a subtle but very important detail.

Once Aborted, Always Aborted


Let's prove it
const controller = new AbortController();

console.log(controller.signal.aborted);

Output:

false

Now:

controller.abort();

Then:

console.log(controller.signal.aborted);

Output:

true

Can we do:

controller.signal.aborted = false;

No.

It's read-only.

The controller is permanently finished.

Therefore...

Every new request needs a new controller.

This is one of the most important patterns in modern JavaScript.

Instead of this:

const controller = new AbortController();

We do this:

let controller;

Notice it's declared with let.

Why?

Because we're going to replace it repeatedly.
